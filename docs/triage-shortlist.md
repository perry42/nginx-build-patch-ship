# M2 triage shortlist

Data: `docs/triage.csv` (962 rows, 606 unique CVEs; generated by `scripts/triage.py`, rule-based only),
`docs/triage-nginx-upstream.csv` (38 nginx.org advisories whose vulnerable range includes 1.25.5).
Scans: Trivy 0.76.2 and Grype v0.122.1 of `nginx:1.25-bookworm` (digest a484819e...), run 2026-11-24.
Evidence rule: every URL below was opened and read during this triage. Anything not opened is marked UNVERIFIED.

## Corrections to the brief

- **CVE-2024-7347 (mp4)** is real: low severity, buffer over-read in `ngx_http_mp4_module`, vulnerable 1.5.13-1.27.0, fixed 1.27.1/1.26.2. Correct. Tier C.
- **The 2024 HTTP/3 family** is real but the exact set is: CVE-2024-32760, -31079, -35200, -34161 (vulnerable 1.25.0-1.25.5 and 1.26.0, fixed 1.27.0/1.26.1). CVE-2024-24989/-24990 are fixed in 1.25.4, so they do NOT affect 1.25.5. Debian marks 32760 `not-affected` for its own 1.22.1 only because the code is absent there; irrelevant for us.
- **Neither scanner flags any nginx.org CVE.** 0 of the 38 upstream advisories appear in Trivy or Grype. The nginx package is built by nginx.org, so the Debian tracker data does not cover it. Grype only matches two ancient name-matches against Debian's own nginx (CVE-2009-4487, CVE-2013-0337). Applicability to the nginx.org build is UNVERIFIED (not researched; low value).
- **No tier-A nginx CVE exists.** I read the nginx.org CHANGES entry and Debian tracker text of every advisory affecting 1.25.5. Each one needs at least one directive that the default config does not contain (`rewrite`, `ssl`, `http2`, `alias`, `mp4`, ...). The default config is `listen 80; location / { root; index }` plus `error_page`. Evidence: `docker run --rm --entrypoint nginx nginx:1.25-bookworm -T | grep -E "rewrite|ssl|http2|alias|try_files|map |mp4|slice|ssi"` returns only commented or mime-type lines. Also ruled out for the default config: CVE-2026-93479 ("root document and request logging" would be default-reachable, but it only affects 1.31.2-1.31.6, so 1.25.5 is not vulnerable).
  Honest framing for the README: the strongest defensible tier is B.
- **Tier A library: only libc6.** `ldd /usr/sbin/nginx` gives libcrypt, libpcre2-8, libssl3, libcrypto3, libz, libc (owners via `dpkg -S`: libc6, libcrypt1, libpcre2-8-0, libssl3, zlib1g). Only libc6 is exercised by default plain-HTTP traffic. But the 9 libc6 CVEs that bookworm fixes are all about iconv, DNS stub resolver, wordexp, assert(), setuid dlopen. None is reachable from nginx request handling. Tier A is true for the component, not for the CVEs.
- **Scanner blind spot (decision needed, see end).** A backport inside nginx cannot be shown disappearing from a scan, because no scanner reports those CVEs before or after. A `vex.json` statement for them has nothing to suppress.

## (a) BUMP candidates

Important mechanics: `debian:bookworm-slim` (12.15 today) already ships the fixed versions of libc6 and pcre2 and offers libssl3 3.0.22. An unpinned `apt-get install` would also pull them. The "bump" is therefore made deliberate and auditable by pinning the exact version (D8) and recording baseline -> new. All counts below come from triage.csv rows with `proposed_action=bump`.

### B1. OpenSSL: libssl3 3.0.11-1~deb12u2 -> 3.0.22-1~deb12u2 (tier B). RECOMMENDED

- Pin: `libssl3=3.0.22-1~deb12u2` (this is today's bookworm candidate, verified with `apt-cache policy` in bookworm-slim). Build against matching `libssl-dev`. `nginx -V` then shows the new OpenSSL (baseline shows built 3.0.9 / running 3.0.11).
- Clears **48 unique CVEs** on libssl3 (96 rows because the `openssl` CLI package carries the same 48; we do not install the CLI). By Trivy severity: 1 CRITICAL, 9 HIGH, 14 MEDIUM, 24 LOW. 8 libssl3 CVEs stay open (no Debian fix yet, e.g. CVE-2026-107494 QUIC frame queueing, rated HIGH).
- Headline CVEs (both scanners flag them, both are in the bump set):
  - **CVE-2024-6119**: X.509 name-check DoS, CVSS 7.5 (NVD, opened), Trivy HIGH / Grype HIGH, EPSS 0.666, fixed 3.0.14-1~deb12u2. Real for nginx when it verifies certificates (`ssl_verify_client`, `proxy_ssl_verify`). Best "relevant to nginx" story.
  - **CVE-2025-15467**: CMS AuthEnvelopedData stack overflow, Trivy HIGH / Grype CRITICAL, EPSS 0.748, NVD scores 9.8 (CNA 8.8), fixed 3.0.18-1~deb12u2. Debian tracker opened: description says it needs parsing of attacker CMS/PKCS7 content. nginx does not parse CMS, so it is scanner-relevant but not runtime-reachable. Say so plainly.
  - CVE-2026-31789 CRITICAL (32-bit only per description in triage.csv; we are amd64). Another scanner-only item.
- Tier evidence: libssl3 in `ldd`; default config has no `ssl`. TLS is the single most common production addition, hence B.
- Debian Security Tracker pages opened: https://security-tracker.debian.org/tracker/CVE-2025-15467 and https://security-tracker.debian.org/tracker/CVE-2026-84782. For CVE-2024-6119 the tracker page was NOT opened (UNVERIFIED); NVD JSON was.
- NVD: https://nvd.nist.gov/vuln/detail/CVE-2024-6119 and https://nvd.nist.gov/vuln/detail/CVE-2025-15467 (queried via API).
- PoC/test angle: no exploit needed. Test = `nginx -V` shows the new OpenSSL, `openssl version` not applicable; plus TLS parity (handshake, ALPN h2, cipher) between old and new images with a self-signed cert. Scanner delta is the proof: Trivy/Grype rows for libssl3 drop from 56 to 8 (expected, UNVERIFIED until the new image is scanned).
- Difficulty: trivial (one pin). Risk: low (same Debian ABI, 3.0.x).
- What this means (interview): "OpenSSL is the TLS library nginx links. The base image froze a 2023 build, so 48 later advisories apply by version. I pinned the exact fixed Debian build, rebuilt nginx against it, and re-scanned to see those rows disappear. Some of them (CMS) nginx never calls, and I say so; the one that really matters for nginx is the X.509 name check."

### B2. glibc: libc6 2.36-9+deb12u7 -> 2.36-9+deb12u14 (tier A by linkage)

- Pin: `libc6=2.36-9+deb12u14` (+ libc-bin same version; already in bookworm-slim 12.15).
- Clears **9 unique CVEs** (18 rows incl. libc-bin): 6 MEDIUM, 3 LOW: CVE-2025-0395, -15281, -4802, -8058, CVE-2026-0861, -0915, -4046, -4437, -4438. 30 other libc6 CVEs stay open (`affected`/`fix_deferred`, no bookworm fix).
- Debian tracker opened: https://security-tracker.debian.org/tracker/CVE-2026-0915 (bookworm fixed in 2.36-9+deb12u14; CVSS 7.5 per NVD, opened). The tracker lists the fix as `deb12u14`; the "(security) 2.36-9+deb12u7 vulnerable" line in the tracker is the old security-suite version.
- Value: only candidate whose component is tier A (every request runs through libc). Weakness: no CVE here is reachable from HTTP handling, all low EPSS (<0.01). Good as a secondary pin, weak as the headline.
- Difficulty: trivial. Risk: low.
- What this means: "libc is loaded by every nginx process even in the stock config, so it earns tier A. The specific bugs fixed are in functions nginx does not call, so this reduces scanner noise and exposure surface rather than closing a live attack path."

### B3. PCRE2: libpcre2-8-0 10.42-1 -> 10.42-1+deb12u2 (tier B)

- Pin `libpcre2-8-0=10.42-1+deb12u2` (in bookworm-slim). Clears **7 CVEs**: 4 HIGH (CVE-2026-103111 CVSS 7.6, CVE-2026-86145 8.2 per NVD; -89157, -89161), 3 MEDIUM. All Trivy+Grype.
- Caveat: the flaws trigger on attacker-controlled regex patterns. In nginx the patterns are in the admin's config, not the client's request. NVD entries are "Awaiting Analysis"/"Deferred" (opened), so scores are provisional. Tracker page NOT opened (UNVERIFIED).
- Use as an extra, not a headline.

Not a bump candidate: **zlib1g 1.2.13**. Debian has no bookworm fix; findings are `affected`/`will_not_fix`. CVE-2023-45853 (CRITICAL 9.8) is MiniZip, which Debian's tracker (opened) says is not built into the zlib binaries ("contrib/minizip not built"), so it is a scanner false positive, a good `not_affected` VEX extra. CVE-2026-85091 (HIGH): tracker (opened) says bookworm `vulnerable` but the gz_write non-blocking code was introduced in 1.3.1.2, so bookworm 1.2.13 is likely NOT affected (UNVERIFIED, the upstream issue was not opened).

## (b) BACKPORT candidates (all verified against the nginx-1.25.5 tarball with `patch --dry-run`; nothing built)

Upstream repo: https://github.com/nginx/nginx. Mainline commit hashes below equal the stable-branch commits that the Debian tracker cites (same diff, verified by reading both).

### P1. CVE-2026-42945: rewrite module heap overflow (tier B). RECOMMENDED

- Advisory: https://nginx.org/en/security_advisories.html (medium per nginx; fixed 1.31.0 / 1.30.1; vulnerable 0.6.27-1.30.0, so 1.25.5 is affected). CHANGES text: https://nginx.org/en/CHANGES (1.31.0).
- CVSS: 8.1 v3.1 (NVD and F5 CNA), 9.2 v4.0 (F5). NVD: https://nvd.nist.gov/vuln/detail/CVE-2026-42945
- Debian tracker (opened): https://security-tracker.debian.org/tracker/CVE-2026-42945. Cites commit https://github.com/nginx/nginx/commit/524977e7c534e87e5b55739fa74601c9f1102686 (release-1.30.1); mainline twin 2046b45aa0c6e712c216b9075886f3f26e9b4ca9 ("Rewrite: fixed escaping and possible buffer overrun").
- Patch: **one added line** in `src/http/ngx_http_script.c`, `ngx_http_script_regex_end_code()`: `e->is_args = 0;`. Applies cleanly to 1.25.5 (no offset, no fuzz). Difficulty: trivial; the backport is the easy part, the explanation is the substance.
- Tier: B. Needs `rewrite` with a `?` in the replacement, followed by `rewrite/if/set` reading `$1`. Not in the default config; very common in real configs. Evidence: `nginx -T` default shows no rewrite.
- Scanner visibility: **none** (0 of 38 upstream advisories flagged by Trivy or Grype).
- PoC (actually ran it on the baseline image, `nginx:1.25-bookworm`, config from the commit message):
  ```
  location /a/ { rewrite ^(.*) /new?c=1; set $myvar $1; return 200 "myvar=[$myvar]\n"; }
  curl --path-as-is "http://localhost:18080/a/x%20y%26z%2Fq"
  -> myvar=[/a/x%20y%2]
  ```
  The correct value is `/a/x y&z/q`. The baseline returns an escaped AND truncated string, i.e. the buffer was sized without escaping and the escaped copy was written into it. Deterministic, no crash required, so it is an ideal parity/regression test: expected after patch `myvar=[/a/x y&z/q]` (UNVERIFIED until we build). Config saved at `scans/tmp/poc/rw.conf`.
- What this means: "nginx has a tiny script engine behind `rewrite`/`set`. After a rewrite that adds a query string, it forgot to reset an 'I am inside the query string' flag. Later captures were escaped (longer) but the output buffer was sized for unescaped text, so it wrote past the heap buffer. The fix is resetting that flag. I can show the bug on the old image with one curl and show it gone on mine."

### P2. CVE-2026-9256: rewrite overlapping captures (tier B). Natural pair with P1

- nginx: medium (fixed 1.31.1 / 1.30.2; vulnerable 0.1.17-1.31.0). CVSS 8.1 v3.1 / 9.2 v4.0 (NVD, opened).
- Tracker (opened): https://security-tracker.debian.org/tracker/CVE-2026-9256; commit https://github.com/nginx/nginx/commit/3f135ae2eb60ce376196c898a6c7cb4d774f7068 (release-1.30.2), mainline ca4f92a27464.
- Patch: 13 insertions, 7 deletions in `ngx_http_script_regex_start_code()`. Applies cleanly to 1.25.5, and cleanly after the P1 patch (tested sequentially on a copy). Medium-small; the change recomputes the buffer length per capture including escaping.
- PoC from the commit message: `rewrite ^/((.*))$ http://127.0.0.1:8080/?$1$2;` with URI `/++++++++++++++++++++++++++++++` overflows the heap. Baseline returned a 302 with no visible symptom (I ran it), so the overflow is silent without ASan; use a differential test on the Location header instead (UNVERIFIED expected values).
- Recommendation: do P1 + P2 as ONE backport theme ("rewrite module hardening", 2 patches, 2 CVEs). Counting both is honest, but the assignment says quality over quantity: one fully proven CVE is enough.

### P3 (alternative, tier B). CVE-2026-118899: infinite loop reading request body over TLS 1.3

- nginx "major", vulnerable 1.13.0-1.31.8, fixed 1.31.9 / 1.30.7. CVSS 7.5 v3.1 / 8.7 v4.0 (NVD, opened). Tracker (opened): https://security-tracker.debian.org/tracker/CVE-2026-118899, commits 1b723277aa55 (request body, 3 lines: `n = NGX_AGAIN;` and `n == NGX_AGAIN ||`) and d1640655f46c (HTTP/3 twin, optional). Both apply to 1.25.5.
- Needs `listen ... ssl` + TLS 1.3 + a body read. Pros: DoS of the whole worker, high impact. Cons: a PoC needs a crafted TLS peer (WANT_WRITE condition), hard to test deterministically, so the test-agent could only check "TLS body POST still works" (UNVERIFIED there is any public PoC).

### Tier C extras (not recommended as the counted backport)

- **CVE-2026-123007** HTTP/2 flow control (major, 8.1/9.2, tracker opened, commit b89c4100bf67 = mainline e27f5fa84fe6, 3 files, applies with offsets). Tier B by usage but needs `http2`; a flow-control exploit needs a custom HTTP/2 client (public write-ups are cited in the tracker, not opened = UNVERIFIED). Larger, riskier to reason about.
- **CVE-2026-125283** try_files+alias (nginx "minor", 5.3). Needs alias + try_files + map variable; commit b99b6b528b64, one line; tier C.
- **CVE-2024-7347** mp4 over-read (low, CVSS 4.7 v3.1). Official patch, a 3-hunk diff, published at https://nginx.org/download/patch.2024.mp4.txt (opened; applies with `-p1`, clean). Tracker (opened): commits 88955b1044ef and 7362d01658b6. Needs `mp4;` in a location (not in default) and a crafted mp4 with unordered `stsc` chunks to test. Pros: the only advisory with an officially published standalone patch. Cons: low severity, tier C, PoC requires hand-crafting an MP4.
- **2024 HTTP/3 family**: nginx.org advisory https://mailman.nginx.org/pipermail/nginx-announce/2024/GMY32CSHFH6VFTN76HJNX7WNEX4RLHF6.html is linked from the advisories page (link seen, page itself NOT opened = UNVERIFIED). Fixes in 1.27.0 span ~7 commits (`HTTP/3: fixed dynamic table overflow`, `QUIC: ...`, etc.; list from GitHub compare 1.25.5...1.27.0, the CVE-to-commit mapping UNVERIFIED). Needs `listen ... quic`; large and hard to test. Not recommended.

## Recommendation

1. **Bump: B1 OpenSSL libssl3 -> 3.0.22-1~deb12u2** (48 CVEs, visible in both scanners, headline CVE-2024-6119), plus B2 libc6 pin as a secondary (tier A story, 9 CVEs) and optionally B3 pcre2.
2. **Backport: P1 CVE-2026-42945** (one-line patch, real vulnerability, demonstrable on the baseline with one curl, deterministic regression test), optionally with P2 CVE-2026-9256 in the same area.

## Decisions for the candidate

1. **Scanner-visible backport?** nginx upstream CVEs are invisible to both scanners, so the VEX demo (`trivy/grype --vex` suppressing a finding) cannot show a before/after row for P1. Options: (a) accept and prove the fix by the PoC test plus a `vex.json` `fixed` statement, documenting why scanners cannot see it (my recommendation: it is the honest result); (b) backport into a Debian library that scanners DO flag, e.g. zlib CVE-2026-27171 (MEDIUM, both scanners, upstream fix ba829a458576 in zlib 1.3.2 per tracker), which means rebuilding zlib1g, extra scope and a second custom package. Please decide.
2. Is a bump that equals "current bookworm" acceptable as long as it is pinned and documented? (Recommendation: yes, say it honestly.)
3. Module packages (geoip, image_filter, njs, xslt): shipping them keeps parity but brings ~270 tier-C rows (libheif, libtiff, libxml2, ...); dropping them is an "extra" and not a counted fix. Not decided in triage.
4. Do we count P1 and P2 as two backports or one theme? One fully proven CVE beats two half-proven.
5. A note on dates: CVE IDs and versions in the sources are dated up to 2026-11-23 (nginx 1.31.10). Pinned versions will drift; the script records the apt candidate date (2026-11-24).
