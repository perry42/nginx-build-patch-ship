# Triage decision: the two CVEs we fix

**Status: DECIDED. Main backport: nginx-core CVE-2026-42945 (reachable, CVSS 8.1, functional test). Second backport, for the scanner/VEX demonstration: zlib CVE-2026-27171. Main bump: OpenSSL (`libssl3`). Extra bumps at the end, once the mandatory items work: other fixed bookworm libraries (libc6, pcre2, ...), each pinned and recorded.**

Baseline: `nginx:1.25-bookworm` (nginx 1.25.5), digest `sha256:a484819eb60211f5299034ac80f6a681b06f89e65866ce91f356ed7c72af059c`.
Full table: `docs/triage.csv` (every finding, generated by `scripts/triage.py`). Candidate analysis: `docs/triage-shortlist.md`.

## 1. Bump: OpenSSL (`libssl3`)
- **Change:** pin `libssl3=3.0.22-1~deb12u2` (baseline has 3.0.11-1~deb12u2) and build nginx against the matching `libssl-dev`.
- **Why:** nginx links it (`ldd /usr/sbin/nginx` shows `libssl.so.3`, `libcrypto.so.3`). Both scanners flag it. The bump clears 48 unique CVEs in one low-risk change (same Debian ABI). Best nginx-relevant example: CVE-2024-6119 (X.509 name check, CVSS 7.5), which applies when nginx verifies certificates.
- **Honest limits:** the default nginx config has no TLS, so reachability is tier B (common config). CVE-2025-15467 (CMS parsing) is cleared but nginx never parses CMS. The fixed version is already in today's `debian:bookworm-slim`; we pin it so the fix is deliberate and reproducible.
- **Evidence:** https://nvd.nist.gov/vuln/detail/CVE-2024-6119, https://security-tracker.debian.org/tracker/CVE-2025-15467

## 2. Backport: CVE-2026-42945 (nginx rewrite module)
- **Change:** apply the upstream fix (one line, `e->is_args = 0;`, upstream commit `524977e7c534`) onto nginx 1.25.5 as `build/patches/CVE-2026-42945.patch`.
- **Why:** it is the kind of fix the brief asks for: a CVE fixed upstream only in later versions, ported onto the version we ship. nginx.org's advisory page lists it as vulnerable 0.6.27 to 1.30.0, not vulnerable 1.30.1+ and 1.31.0+, so 1.25.5 is affected. CVSS 8.1. The patch is small and applies cleanly to 1.25.5 (dry run by the triage agent). A request-level regression test can show before and after.
- **Honest limits:** needs a `rewrite` directive, so tier B, not default config. Neither scanner lists it before or after, so a scanner diff cannot show it; we prove it with a functional test and `vex.json`.
- **Evidence:** https://nginx.org/en/security_advisories.html, https://www.cve.org/CVERecord?id=CVE-2026-42945
- **To verify when patching:** open the upstream commit and confirm the diff and that `patch -p1` applies without fuzz.

## Not fixed, on purpose
Everything else stays in the residual-risk section of the README, with the reason per group (not linked by nginx, no fixed version available, tier C, or optional modules).

## Second backport (VEX demonstration): zlib CVE-2026-27171
- **What:** hand-port upstream madler/zlib `ba829a45` (two `if (len2 < 0) return 0;` guards) onto Debian's zlib1g `1:1.2.13.dfsg-1`, rebuilt with Debian tooling, same version string.
- **Why this one:** the brief needs a backport that the scanners list, so a VEX statement can make the row disappear (items 3, 5, 8). Both scanners list it, Debian has no bookworm fix, upstream has a 2-line fix, the rebuild takes about 25 seconds, and we tested that VEX removes the row (Trivy removes it, Grype moves it to ignored).
- **Why a medium-severity CVE (the interview answer):** the brief grades end-to-end quality, not severity ("two well-fixed beats ten half-fixed"). The severe findings that matter are covered elsewhere: the OpenSSL bump clears the Critical and High libssl3 CVEs. The glibc candidates are rated higher by Grype but need a risky rebuild of an Essential package. A severe nginx-core CVE exists, but the scanners do not list it, so it cannot show a before and after row; it is handled as an extra with a functional test.
- **Honest limit:** nginx only imports `deflate*` and `inflate*` from zlib and never calls `crc32_combine`, so this CVE is not reachable through nginx. We say so in the README.
